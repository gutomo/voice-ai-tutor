# DEMO_RUNBOOK.md — ライブデモ実行手順 (Phase 7)

> 10 から 12 分のライブデモを滞りなく回すための実行手順書。台本そのもの (時間配分と talking point) は
> `docs/DESIGN.md` §6 が一次資料。この文書は「当日どのボタンを押すか」「事前に何をリセットするか」
> 「詰まったときどう逃げるか」を足す。
>
> API レベルの通しリハーサルは `backend/tests/test_demo_rehearsal.py` が自動化している (外部 API はスタブ)。
> 台本の各ビート (ドリル → ロールプレイ → 山場 → まとめメール) が順に成立することを毎回検証できる。

## 0. 当日の登場人物とデータ

- **Live Demo (Siswa)**: 商談で実際に録音するライブ用の学習者。`seed_all` が短いベースライン (ドリル 2 ターン、

## 1. デモ前の準備 (T-15 分)

1. **サービスを起動する** (3 つ)。
   ```bash
   docker compose up -d                                   # Postgres
   cd backend && uv run uvicorn app.main:app --reload      # API (:8000)
   cd frontend && npm run dev                              # フロント (:5173)
   ```
   ヘルス確認: `curl http://localhost:8000/healthz` → `{"status":"ok"}`。

2. **環境変数を確認する** (`backend/.env`)。ライブで実採点・実メールまで見せるなら:
   `AZURE_SPEECH_KEY` / `AZURE_SPEECH_REGION` (発音採点)、`AWS_REGION` と IAM キー ＋ `BEDROCK_MODEL_ID`
   (会話・ルーブリック。推論プロファイル `us.anthropic.claude-sonnet-4-6` を使う。基盤 ID は on-demand 不可)、
   `EMAIL_SENDER` / `TEACHER_EMAIL` (SES。サンドボックスでは宛先も検証済みにする)。

3. **デモデータをリセットする** (冪等。同名のデモ学習者を作り直すだけで実データには触れない)。
   ```bash
   cd backend && uv run python -m app.seed
   ```
   出力の末尾が `Live Demo (Siswa) ... passline= 53.4% ... ← ライブ用ベースライン` なら成功。

4. **自動リハーサルを 1 本流す** (台本が API レベルで通ることの最終確認)。
   ```bash
   cd backend && uv run pytest tests/test_demo_rehearsal.py -q
   ```

5. **ブラウザを整える**。録音する端末 (スマホ or PC) で 📱 Siswa タブを開き、マイク許可を先に済ませておく
   (本番でパーミッションダイアログを出さない)。教師ダッシュボードを見せる用に 🎓 Guru を別タブで開いておく。

## 2. 当日の操作 (DESIGN §6 台本に対応)

| 時間 | 画面操作 | 補足 |
|---|---|---|
| 0:00 | 課題提示 (口頭) | 資料は不要。「アプリ不要・WABA 不要」を最初に言い切る。 |
| 0:30 | 📱 Siswa でドリルのモデル文を復唱 → 録音 → **発音スコアが画面に出る** | ここで **わざと少し外す** (§3)。ScoreCard の要練習語を指さす。 |
| 3:00 | ロールプレイを 1 ターン (AI が利用者役 田中さん)。応答を録音 | 二段採点 (STT → scripted) ＋ ルーブリック。返信音声が TTS で再生される。 |
| 5:00 | 🎓 Guru へ切替。**いまの Live Demo の到達度が上がっている** (**山場**) | ロールを切り替えてもセッションは維持される。同じ 1 名として現れる。 |
| 7:00 | コホート画面。**要フォロー 2 名 (Andi・Putra)** の自動フラグ＋会話ログ | まとめメールの見本は Step 5 で実送信 (下記)。 |

> 録音が失敗しても、押し直せば新しいターンとして保存されるだけで壊れない。

## 3. 「わざと少し外す」見せ場

発音採点の価値は「弱い音を具体的に指摘できる」こと。0:30 の復唱で、モデル文の難しい語 (例:「体温」「血圧」
「眠れましたか」) を **意図的に少しだけ崩して** 発音する。Azure がその語の accuracy を落とし、ScoreCard の
要練習語と、教師ダッシュボードの発音ヒートマップの両方に同じ語が出る。この 2 画面の一致が刺さる。

保険: Azure がライブで崩れを拾えなかった場合に備え、シードした各ターンにはあらかじめ要練習語を 1 つ置いてある
(`_DRILLS` の hard word)。ヒートマップは常に素材を持つので、山場の画面は空にならない。
この 2 経路の一致は `tests/test_demo_rehearsal.py::test_deliberate_miss_surfaces_in_scorecard_and_heatmap`
が検証している。

## 4. 詰まったときのフォールバック

- **発音スコアが出ない / Azure が遅い**: そのターンを飛ばし、シード済みの Dewi (🎓 Guru → 学習者ビュー) で
  発音ヒートマップ・到達度推移・会話ログを見せる。話の筋 (即時フィードバック → 教師が把握) は変わらない。
- **メールが届かない (SES サンドボックス)**: 送信ログの `status` と `MessageId` を画面で見せれば「送った」ことは
  示せる。宛先は `EMAIL_SENDER` にフォールバックするので自分宛に届く。受信は後追いでも可。
- **セッションがおかしくなった**: 📱 Siswa のセッションバーで終了するか、ロールを切り替えて戻ると
  `SessionProvider` が新しいセッションを開く。最悪は手順 3 のシードから作り直す (30 秒)。

(当日足したライブのセッション・ターンごと作り直す)。コホート 6 名も同時に作り直される。
