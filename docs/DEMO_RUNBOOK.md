# DEMO_RUNBOOK.md — ライブデモ実行手順 (Phase 7)

> 10 から 12 分のライブデモを滞りなく回すための実行手順書。台本そのもの (時間配分と talking point) は
> `docs/DESIGN.md` §6 が一次資料。この文書は「当日どのボタンを押すか」「事前に何をリセットするか」
> 「詰まったときどう逃げるか」を足す。
>
> 当日の準備は `cd backend && uv run python -m app.preflight` の 1 本にまとまっている
> (DB 疎通 → デモデータのリセット → 台本の通しスモークを一括、緑/赤で判定。詳細は §1 手順 3)。
> API レベルの通しリハーサルは `backend/tests/test_demo_rehearsal.py` が自動化している (外部 API はスタブ)。
> 台本の各ビート (ドリル → ロールプレイ → 山場 → まとめメール) が順に成立することを毎回検証できる。

## 1. デモ前の準備 (T-15 分)

1. **サービスを起動する** (3 つ。下 2 行は起動したまま常駐するので、各行を別ターミナルで)。
   ```bash
   docker compose up -d                                   # Postgres (常駐)
   cd backend && uv run uvicorn app.main:app --reload      # API (:8000、別ターミナルで常駐)
   cd frontend && npm run dev                              # フロント (:5173、別ターミナルで常駐)
   ```
   ヘルス確認: `curl http://localhost:8000/healthz` → `{"status":"ok"}`。

2. **環境変数を確認する** (`backend/.env`)。ライブで実採点・実メールまで見せるなら:
   `AZURE_SPEECH_KEY` / `AZURE_SPEECH_REGION` (発音採点)、`AWS_REGION` と IAM キー ＋ `BEDROCK_MODEL_ID`
   (会話・ルーブリック。推論プロファイル `us.anthropic.claude-sonnet-4-6` を使う。基盤 ID は on-demand 不可)、
   `EMAIL_SENDER` / `TEACHER_EMAIL` (SES。サンドボックスでは宛先も検証済みにする)。

3. **プリフライトを 1 本流す** (DB 疎通 → デモデータのリセット → 台本の通しスモークを一括、緑/赤で判定)。
   ```bash
   cd backend && uv run python -m app.preflight
   ```
   末尾が `GREEN: デモ準備 OK` なら当日回る。`RED` なら表示された `[FAIL]` を直す
   (最頻は Postgres 未起動 → 手順 1 の `docker compose up -d`)。出力中の
   `Live Demo (Siswa) ... passline= 53.4% ... <- ライブ用ベースライン` がライブの開始点。
   実 API (Azure / Bedrock / SES) の設定状況も advisory で並ぶ (未設定でも §4 のフォールバックでデモ可)。

   > 個別に叩くなら: `uv run python -m app.seed` (リセットのみ) と
   > `uv run pytest tests/test_demo_rehearsal.py -q` (スモークのみ) に分かれる。

4. **ブラウザを整える**。録音する端末 (スマホ or PC) で 📱 Siswa タブを開き、マイク許可を先に済ませておく
   (本番でパーミッションダイアログを出さない)。教師画面の出し方は 2 通り:
   - **単一画面 (推奨)**: 同じタブでアプリ内の 🎓 Guru に切り替える。切替のたび Dashboard は再マウントされて
     最新を自動取得し、セッションは切替をまたいで維持される (§2 5:00 の山場はこの経路。到達度は勝手に最新化する)。
   - **別画面で常時表示**: Guru を別タブ/別端末で開きっぱなしにするなら自動更新は効かない。ライブの 1 ターン後に
     コホート画面右上の **↻ Segarkan** を押して更新する (押さないと T-15 のままで到達度が動かない。学習者ビューに
     入っていると更新ボタンが出ないので、コホート画面に戻ってから押す)。

## 3. 「わざと少し外す」見せ場

発音採点の価値は「弱い音を具体的に指摘できる」こと。0:30 の復唱で、モデル文の難しい語 (例:「体温」「血圧」
「眠れましたか」) を **意図的に少しだけ崩して** 発音する。Azure がその語の accuracy を落とし、ScoreCard の
要練習語と、教師ダッシュボードの発音ヒートマップの両方に同じ語が出る。この 2 画面の一致が刺さる。

保険: Azure がライブで崩れを拾えなかった場合に備え、シードした各ターンにはあらかじめ要練習語を 1 つ置いてある
(`_DRILLS` の hard word)。ヒートマップは常に素材を持つので、山場の画面は空にならない。
この 2 経路の一致は `tests/test_demo_rehearsal.py::test_deliberate_miss_surfaces_in_scorecard_and_heatmap`
が検証している。

## 4. 詰まったときのフォールバック

- **発音スコアが出ない / Azure が遅い**: そのターンを飛ばし、シード済みの Dewi (🎓 Guru → 学習者ビュー) で
  発音ヒートマップ・到達度推移・会話ログを見せる。話の筋 (即時フィードバック → 教師が把握) は変わらない。
- **メールが届かない (SES サンドボックス)**: 送信ログの `status` と `MessageId` を画面で見せれば「送った」ことは
  示せる。宛先は `EMAIL_SENDER` にフォールバックするので自分宛に届く。受信は後追いでも可。
- **セッションがおかしくなった**: 📱 Siswa のセッションバーで終了するか、ロールを切り替えて戻ると
  `SessionProvider` が新しいセッションを開く。最悪は手順 3 のシードから作り直す (30 秒)。

## 5. デモ後のリセット

次の商談に備え、`cd backend && uv run python -m app.preflight --reset-only` を実行すれば
ライブ用学習者は 53.4% のベースラインへ戻る (当日足したライブのセッション・ターンごと作り直す。
スモークを省くので数秒)。コホート 6 名も同時に作り直される。
